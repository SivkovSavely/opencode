# SQLite execution capture (V1 fork)

Set `OPENCODE_SQLITE_EXECUTION_DIAGNOSTICS=1` in the server process environment before starting it. Setting `OPENCODE_HANG_DIAGNOSTICS=1` as well enables the separate hang timeline; either option works independently. The SQLite trace is off by default and is not available on Windows, where POSIX modes cannot guarantee private capture files. Use it for a short capture only: it does synchronous filesystem writes, which can affect timing.

After a controlled restart of the **existing** service with the updated binary, verify that the new PID has a capture directory under `$XDG_DATA_HOME/opencode/log` (default `~/.local/share/opencode/log`, using the service's environment). The directory is named `sqlite-execution-<pid>-<random>` and is created on the first SQL execution. It is not relative to `OPENCODE_DB`. Each capture retains only `queries.jsonl` and, after rotation, `queries.previous.jsonl`, at most 4 MiB each. The directory and files are owner-only. Remove old capture directories after use; rotation is per process, not across restarts.

Watch the active file from a separate shell with `tail -n 20 -F /path/to/capture/queries.jsonl`. If the service stops responding, preserve both files promptly. Match `sqlite_query_start` and `sqlite_query_end` by `queryID` within the capture. A fresh start with no end during the hang is the first candidate; if the query returns, use the end's `durationMs` and `status`. A run of short pairs with the same `statementID` indicates repeated executions instead. Correlate with the existing hang JSONL under `log/hang-diagnostics/` by `pid`, `wallClock` and `uptimeMs`, and with database snapshots by `databaseID` and `fiberID` when present.

The start includes a redacted `shape`, result `mode`, and source locations captured at Drizzle submission, with the active Effect stack as a fallback. Locations may be absent where the runtime has no useful frame. Compiled Bun and bundled Node locations can be bundle offsets even without source maps; keep the matching build and source revision. `statementID` is an opaque fingerprint of the SQL template, stable within the capture and independent of bound values, but not comparable across restarts. The trace does not contain raw SQL, parameters, results, or native error messages. Failed trace writes disable tracing for the process without failing SQL. A start is written synchronously before preparation/execution so another process can read it during a hang; this is not a guarantee against power loss.

The Bun and Node application adapters cover Effect Drizzle rows, values, and transactions, including savepoint and rollback statements, plus the startup compatibility probe and WAL pragma. The unused-in-server legacy native Drizzle handle, stand-alone database tools or shell, TUI direct readers, and separate process-lock database used by server auth handlers are not traced. Do not open or query the production DB to collect the trace, run a second server against it, or run `EXPLAIN` on the live service during the hang. Investigate the shape and originating code offline. After capture, remove the flag and restart normally.
